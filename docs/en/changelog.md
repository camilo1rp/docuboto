# Changelog

All notable changes are documented here.

Format: [Keep a Changelog](https://keepachangelog.com/en/1.0.0/)

> Domain glossary (Colombian SGDEA — *Sistema de Gestión de Documentos Electrónicos de Archivo*, electronic records management system): **radicado** = an officially registered document with a unique, immutable tracking number; **expediente** = a logical case file grouping related radicados; **TRD** (*Tabla de Retención Documental*) = document retention schedule; **TVD** (*Tabla de Valoración Documental*) = valuation schedule for an accumulated/backlog fonds (documentation already produced without archival criteria, typically from suppressed units or liquidated entities); **dependencia** = organizational unit; **FUID** (*Formato Único de Inventario Documental*) = standard documentary inventory form; **PQRS** = citizen petitions, complaints, claims and suggestions; **índice electrónico** = electronic index that gives the electronic expediente legal validity.

### Added

- `feat(archive)`: **TVD — valuation schedule for an accumulated fonds (ADR-026, Increment 1: registration and convalidation, migration 039)** — an entity holding an accumulated fonds (documentation already produced without archival criteria, typical of suppressed units or liquidated entities) had nowhere to register its valuation instrument, and therefore could neither close nor dispose of anything in that fonds. The TVD enters as **the same instrument as the TRD**, with the same convalidation circuit (Comité → Consejo → RUSD → publication): a discriminator on the existing table, not a new table, so the single point on which seven irreversible WORM retention writes depend is not forked. Four layers protect it: a series code can belong to only one instrument; listings are always read through a view that already filters by type; each instrument's own content (fonds, extreme dates, valuation rationale for the TVD) is mandatory or forbidden depending on the type, enforced by the database; and — most important in this increment — **no expediente can yet be classified under a TVD** (the database blocks it outright), so the irreversible-retention risk is zero until that piece exists. Routes `/api/v1/tvd` mirror the TRD ones (create, edit, version, approve, return, convalidate, register RUSD, repeal), same permission as TRD. Full version-history lookup (`GET .../{code}/versiones`) was also added for both TRD and TVD — promised in the previous increment and never built. — *Why*: a records-compliance audit finding on the retention model: an entity with an accumulated fonds had no way to appraise it inside the system.
- `feat(frontend)`: **`/admin/interoperabilidad` — export/import of radicados, batch loading and postal tracking (Phase 8, last of the API↔UI drift closure)** — five backend capabilities had been ready for a while with no screen using them: exporting a ZIP package of radicados, importing it back preserving the original tracking number, creating documents or expedientes in batch, and querying a shipment's tracking against the postal operator. The new screen covers the first four in tabs; the last one was added as an "Update tracking" button in the existing `/envios` tray. The most delicate part is import: it is all-or-nothing (if a single file in the package does not match its declared fingerprint, nothing is imported) and when that happens the screen shows exactly which file failed and why, never a generic "import failed". Batch loading, being a bulk write over official documents, requires confirming the exact item count before executing, and while processing it polls progress every two seconds, always distinguishing "could not query the status" from "no results yet" (a fabricated zero progress is never shown). Postal tracking, having no real operator integration yet, says so explicitly instead of faking a live query. While building the screen it turned out batch loading could not work at all — the gateway had no route registered for those two endpoints. That was fixed (see *Fixed* below), but the fix changed the shape of the status URL and the screen kept the old one; combined with a reactivity defect in the progress panel, batch loading reported no result under any circumstance. The UX review of 2026-08-02 caught it, and it is **now fixed** in that review's own entry below. Export, import and postal tracking did work end to end from the start. — *Impact*: 1 new screen with 4 sections, 1 new button in postal shipments, 27 new automated tests.

### Fixed

- `fix(auth,frontend)`: **the interface offered actions the server was going to reject, because it did not know what level each permission was granted at (third batch of the user-experience review)** — a permission in this system is not a yes or a no: it has a **level** — look up, edit, create or delete. The server knows it and enforces it; the interface never received it, because the lookup that tells it who the user is resolved the level and then **threw it away**, sending only the list of names. The result: someone holding a read-only permission was offered Close, Transfer, Exclude or Sign acta buttons, and got a "you do not have permission" when they pressed them. The two user-experience reviews, carried out separately and blind to each other, reached the same conclusion, and **both refused to fix it screen by screen**: the problem was not in the screens but in what the server tells them. It was fixed in both halves. The server now also sends the level of each permission, **without removing anything it already sent**, so nothing already running breaks and no coordinated update is needed. And the interface learns to ask by level, with a deliberately strict rule: if the level does not arrive — a session opened before this change, for instance — the answer is **no**, never "I don't know, so I'll allow it". Applying it meant reviewing **every** button that writes, one by one, against what its service actually requires. That corrected the finding's own premise: most operations only ask for the lowest level, so **only four screens** needed the high restriction. Requiring more would have been the same mistake in reverse, hiding functions from people who are entitled to use them — and doing so silently. It was noted, without being touched, that the inbox has exactly that shape: the interface asks for a permission the server does not require, because there whoever may act is decided by holding the assigned step, not by a permission. — *Why*: the interface must be a faithful mirror of what the server authorizes; offering what is going to be rejected is a functional failure, not a cosmetic one. — *Impact*: no database changes. 199 authentication-service tests and 1370 frontend tests green, including one that reproduces exactly the reported case.
- `fix(frontend)`: **accessibility: insufficient contrast, tables unreachable without a mouse, errors not announced on their field, and AI suggestions that were never announced (second batch of the user-experience review)** — four problems that left part of the users out. **One**: white text on the brand green did not reach the minimum required contrast, and not in a transient effect but in permanent states — the current step number in the two-factor, signature-credential and signing wizards; the active turn in the signature chain; the active filters in drafts and dispatches. In several places it was **the other way round**: the legible tone was used only on mouse-over. **Two**: wide tables cut off the Status and Actions columns on the right, and those that did scroll could not be scrolled with the keyboard, so anyone not using a mouse could not reach them. It was fixed in the two shared table components, so the fix reaches most screens. **Three**: on the profile screen, all seven validation error messages appeared only as a floating notice and never next to the failing field — precisely on the screen that governs the electronic signature credential; they are now announced on the field, and the one-time codes open the numeric keypad and autofill. **Four**: AI suggestions appeared without notifying screen-reader users; they are now announced, without touching the content, which already met the regulatory requirement to cite sources and warn that it was AI-generated. Two honest caveats: the table containers left unmodified wrap a component whose scrolling is already reachable, and giving them another keyboard stop would have created an empty destination; and the original finding mentioned four tables with one cell too many, which a sweep of all 28 tables in the project **could not reproduce** — recorded as such rather than forcing the figure. — *Why*: an actions column invisible on mobile, or an error a screen reader cannot locate, are not finishing details: they prevent the task from being completed. — *Impact*: 1348 tests green. The two-factor recovery code is deliberately left out: it is a server-side gap and must not be papered over in the interface.
- `fix(frontend)`: **batch loading never reported its result, three administration cards led to "no permission", and two screens were not linked (UX review, first batch of fixes)** — the ~20 screens built to surface everything the backend already exposed were implemented without going through the UX/accessibility review, the last step of the project's process. The review was done afterwards and found three **functional** problems, not cosmetic ones; this is its first batch of fixes. **One**: document and expediente batch loading never reported its result, due to two compounding defects — the progress panel did not refresh, and the screen polled progress at an address that had ceased to exist when the routing was fixed. An administrator could load a thousand radicados and have no way of knowing whether they were created or whether everything failed. **Two**: three cards in the administration panel advertised a permission different from the one the server actually requires, so they led to a "you do not have permission" screen; the Interoperability case was doubly wrong, because it also hid the entire screen from a registration operator who could use part of it. All **sixteen** cards were checked, not just the three found, because this same pattern had already resurfaced four times. **Three**: two finished screens — digital preservation and signing keys — were missing from the administration index, which presents itself as the complete map, and were reachable only by typing the address by hand. The root cause of the first failure was fixed too: several code comments asserted things that had stopped being true (that the gateway did not route batch loading, that the metadata services did not require a permission). This is the third time in this release that a stale comment has caused a real defect, so they were deleted rather than left sitting next to the fix, and tests were added that pin the exact address each screen asks the server for, so a route change cannot silently break it again. — *Why*: a screen signed off as finished and documented as complete had its main function inoperative; building the UI reveals the capabilities, but only the review reveals the UI. — *Impact*: batch loading reports its result; the administration panel stops offering what it will deny and stops hiding what it authorizes; two screens stop being invisible. 1339 frontend tests green.
- `fix(repo)`: **four files of the interoperability screen never made it into the repository** — an exclusion rule written for one specific folder at the project root was written unanchored, so it applied to **any** folder with that name anywhere in the tree. It matched the folder holding the document batch-loading files, which therefore stayed out of the history despite being documented as delivered: in the official copy of the project, the screen called addresses that did not exist there. Fixed by anchoring the rule to the root. — *Why*: it surfaced when re-running the work on a clean copy; the earlier review could not see it, because it reads the working files and there they were present. — *Impact*: none on application behavior. The lesson is that this kind of exclusion fails **silently**: the file simply never shows up as pending to save.
- `fix(document)`: **audit trail for batch radicado creation + reactivation of the batch test suite** — batch radicado creation (`POST /api/v1/batch/documents`) left no trace whatsoever in the immutable audit log: hundreds of official documents, each with a unique tracking number, could be created with no record of who did it or when. It surfaced because the twin batch operation over expedientes, in another service, had done it from day one — two mirror functions, only one leaving a trace. Fixed by writing one audit entry **per radicado created** (not one per batch, so individual traceability is not lost), always attributed to the person who submitted the batch, and in such a way that a partially successful batch (say 480 of 500) records exactly what went in and what did not — never the original intent. In addition, this feature's automated test suite had been fully disabled since it was written (it referenced a test fixture that never existed). It was rewritten from scratch, also covering the permission gate that had recently been added with no test verifying it. — *Why*: mass-creating official documents with no record of authorship is precisely what the audit log exists to prevent; a disabled test suite protects nothing, least of all a freshly added permission gate. — *Impact*: no schema change (the audit table already existed). document-service suite: 284 passing, 20 skipped (previously 273 passing, 25 skipped — the remaining 20 are integration tests against a real database, unrelated to this change).
- `fix(api-gateway,document,archive)`: **batch loading unreachable — missing gateway route and an ambiguous status contract between services** — closes the item left open by the interoperability screen: the gateway had no route registered for `/api/v1/batch/`, so both document and expediente batch loading always returned "route not found". Investigating it surfaced a deeper problem: the two services serving batch loading share the same base path, and the job-status lookup (`.../batch/{id}/status`) had **the identical shape** in both — there is no way for the gateway to guess, from the job id alone, which of the two to ask. The fix nests the status lookup under the job type (documents or expedientes), just as creation already did, so the routing decision is unambiguous. Along the way, document batch loading now requires the same permission as creating a document one at a time — it previously required none, unlike the expediente equivalent. — *Why*: without that route the already-built batch screen could not work; the contract shared by the two services had to be disambiguated at the source, not patched around. — *Impact*: batch status URLs change shape — and the screen consuming them kept the old shape, fixed later in the UX review entry; document batch loading gains permission enforcement. What this change left open — batch radicado creation without an audit entry — is **closed** by the first entry in this release.
