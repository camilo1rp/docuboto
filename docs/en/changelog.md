# Changelog

> Domain glossary (Colombian SGDEA — *Sistema de Gestión de Documentos Electrónicos de Archivo*, electronic records management system): **radicado** = an officially registered document with a unique, immutable tracking number; **expediente** = a logical case file grouping related radicados; **TRD** (*Tabla de Retención Documental*) = document retention schedule; **TVD** (*Tabla de Valoración Documental*) = valuation schedule for an accumulated/backlog fonds (documentation already produced without archival criteria, typically from suppressed units or liquidated entities); **dependencia** = organizational unit; **FUID** (*Formato Único de Inventario Documental*) = standard documentary inventory form; **PQRS** = citizen petitions, complaints, claims and suggestions; **índice electrónico** = electronic index that gives the electronic expediente legal validity.

## [Unreleased]

### Baseline v0.01 — what the system does

> **How to read this file.** OrpycaMCP has not cut a release yet: everything below
> is one unpublished baseline. The Spanish changelog keeps the entry-by-entry
> record of how it was built — every audit finding, remediation and increment,
> in the project's working language. This section states what v0.01 **is**, which
> is what an evaluator coming from outside needs; the individual entries that
> follow it cover selected changes and are not a complete log.

**Records management core (E01/E02/E03/E07)** — Registration of incoming, outgoing
and internal documents with an immutable tracking number, assigned atomically per
year + type + tenant. Expedientes (case files) with a full lifecycle
(`open → closed → transferred`), foliation, ZIP export and metadata templates
validated against a JSON Schema per documentary type. Attachments are SHA-256
checksummed on upload, deduplicated per tenant, streamed in chunks (never buffered
whole), and served through document-service so every download passes the clearance
gate.

**Retention and disposition (E04)** — TRD (retention schedule) and TVD (valuation
schedule for accumulated fonds) as a single instrument with two discriminators,
sharing one convalidation circuit: Comité approval, Consejo convalidation, RUSD
registration, publication and repeal — each with its administrative act recorded,
immutable once convalidated (enforced by a database trigger, not only by the
application). Final disposition per radicado and per expediente, with a mandatory
justification on the destructive path.

**Electronic index and signature (E15/E06/E17)** — Append-only versioned XML index
(RT-15 profile v4) with a per-document fingerprint and independent verification.
The index is signed at closure with an institutional XAdES-B/T/LT/LTA signature
(local CA, timestamp, long-term validation material), and transfer actas carry
per-user personal signatures whose role is derived from identity, never chosen by
the client. Personal PKI credentials are enrolled, renewed and revoked in-system,
with a versioned key-encryption keyring and purge of revoked material.
**Not accredited**: this is art. 7 electronic signature, not art. 28 — no ONAC
certificate, no HSM under sole signer control, no accredited TSA.

**Preservation (E10/E12)** — Preservation plan, PREMIS events, AIP packaging
(BagIt/PREMIS) and real PDF/A validation through veraPDF. WORM protection via
MinIO Object-Lock in `COMPLIANCE` mode over the signed index and the transfer
acta, with retention derived from the retention schedule. Primary and secondary
transfers with fixity re-verification on receipt. **Not accredited**: the
repository itself is not an accredited preservation repository.

**Security (E08)** — Multi-tenant isolation by PostgreSQL schema, with the
`search_path` switched per request from JWT claims and MinIO buckets scoped per
tenant. RBAC plus security clearance (no-read-up) applied in the `WHERE` of every
query and inside every write — never as a prior check, so authorization and
mutation are one act. Hash-chained immutable `audit_log`, partitioned monthly and
hardened per partition. Publication is an explicit, justified and audited act
(Ley 1712/2014 art. 12): absence of a reservation decision no longer means
"public".

**Workflow, notifications and search (E05/E16/E09/E19)** — Routing between
dependencias with assignment, transfer, step completion, transaction execution and
rollback, plus automatic routing rules. Email and in-app notifications with a
dead-letter queue and replay. Full-text search embedded in PostgreSQL (no separate
search service), reports, public lookup by verification code, and IMAP mail
ingestion.

**Interoperability (E11/E20)** — OAI-PMH harvesting (Dublin Core and EAD 2002 /
ISAD(G)), CMIS browsing and content retrieval, interoperable export and import of
radicados preserving the original tracking number with mandatory fixity, signed
outbound webhooks and an inbound postal-operator callback with per-tenant HMAC.
Every public channel ships **off** and trims at the source through a single
chokepoint. **Stub**: the concrete connector for a given postal operator.

**AI (E18/E21)** — An MCP server exposing the gateway's capabilities as tools, a
conversational assistant, and a knowledge-service doing retrieval-augmented
generation over pgvector with sovereign embeddings, ACL pre-filtering that fails
closed, and answers that always carry their citations.

**Frontend (E22)** — SvelteKit application with OAuth2 PKCE login, around 40 screens
covering the tray, expedientes, signatures, transfers, physical archive, search,
reports and the entity's own administration. The access token never reaches
client-side JavaScript: every gateway call goes through SSR.

**Operations** — Production Docker Compose manifest verified against real
containers, nginx template, backup and restore programs exercised end to end
(including audit-chain verification after restore), upgrade and rollback
procedure, CI running lint, unit, real-database and frontend tests across all
eleven services, and per-request tracing propagated from the edge.

### Added

- `fix(document,frontend)`: **the publication act had no screen, and its result could not be read** — closing block 11 changed `publicable`'s default to `FALSE` — correctly, because publishing is a decision of the entity and not the consequence of not having classified (Ley 1712/2014 art. 12). What was missing was the legitimate door: `POST /documents/{id}/publicacion` existed, the gateway routed it, and **no screen called it**. An institution that updated was left with every radicado non-publishable and no way to publish any of them from the application: the publication scheme became unexecutable except through SQL. A leak was closed and the system was left without the door. A second defect surfaced while building the screen: `publicable` could be **written but not read** — it was in neither the radicado detail nor the listing, so neither could the UI offer the act over a known state nor could the entity attest through the API to what it had published. A publication scheme that cannot be consulted is not a scheme, it is a blind write; the mapping crosses three layers (SQL query → domain object → response) and the field was missing in all three. The screen is a side panel in the tray that reads the state from the server and always offers the act **opposite** to the current one — publish or withdraw — with a mandatory justification in both directions and an explicit warning of what publishing does: the radicado becomes harvestable over OAI-PMH and CMIS. Over a reserved or annulled radicado **no form is offered**: the backend answers with a neutral `404` (deliberately indistinguishable from "does not exist", so as not to be an oracle over classified material), and letting someone draft a justification only to receive "does not exist" afterwards would be a screen that deceives. The button requires the backend's real threshold — `PERM_RECLASIFICAR` at write level: asking for less produces a 403 on click, asking for more hides it from those who may act. — *Why*: a decision the law requires an entity to make, and to attest to afterwards, cannot depend on direct database access — *Impact*: radicados are still born non-publishable; there is now a way to publish them and a way to consult what was published. Rebuild the document-service and frontend images.

- `fix(shared,gateway,document,archive,auth,storage,infra)`: **publishing stopped being a decision, and an incident could not be followed end to end (production audit, block 11)** — **What gets published is now decided, not inferred.** Two harvesting channels let other institutions and the public collect the entity's records. Until now anything not marked as reserved went out through them — that is, **having decided nothing was equivalent to having decided to publish**: a freshly registered radicado, or one declassified for an unrelated purpose, left on its own. Ley 1712/2014 art. 12 asks for the opposite: a publication scheme, an act by which the entity decides what it disseminates. Each radicado now carries a publication flag that starts **off** and only turns on through an explicit, justified and recorded act, stamped with who did it and when; the `UPDATE` demands `nivel_seguridad = 1` in its own `WHERE`, so a false claim cannot be stored that the next declassification would turn into publication. **An incident could not be traced across services.** `X-Request-Id` had always been on the forwarded-header list — and the gateway generated it in the **response** middleware, after proxying: the pipe was laid and nothing flowed through it. It is now assigned on the way in (pure ASGI, so block 4's chunked streaming survives), travels through every service, comes back to the browser, and each service writes one structured line with entity, user, operation and duration — never the query string. **Example passwords that actually worked.** This repository is public, and two secrets — the electronic-signature key and the object-store credentials — shipped with a **working** example value: an institution that forgot to change them got no warning. Both now default to `""` and the service **refuses to start** without them. The identity-server sample config, which contained two published-password users (one an administrator), is renamed to `realm-dev.json`, and production starts from a `realm-prod.json.example` template that cannot be used unfilled. **CORS `*` with credentials was hardcoded.** Starlette cannot answer `*` with credentials, so it reflects the incoming `Origin` — that is not permissive, it is CSRF. It is now off by default (the product does not need it) and whoever opens it must enumerate the origins (`CORS_ALLOW_ORIGINS`). **The deployment guide told you to copy a template that did not exist**: `infra/nginx.conf.example` is now included and validated with a real `nginx -t`, with HSTS and `X-Forwarded-Proto/Host/For` — without it, login did not complete, the IP sealed into the immutable audit trail was the reverse proxy's own, and large downloads buffered in memory again. **Migration bookkeeping was kept in duplicate.** Two runners (`services/*/migrations/runner.py` and `init_tenant.py`) recorded applied work in three registries invisible to each other, keyed by the **bare filename** — and each service numbers its own series from 001, so four names collide (`002_batch_jobs.sql` between archive and document; the `005`/`006`/`007` dead-letter ones between notification and signature). The second service's runner therefore saw the name and **skipped a migration of its own that had never been applied** — silently, with no error. Harmless so far by coincidence (all four are idempotent and nearly identical). There is now a single ledger, `public.schema_migrations`, keyed by schema + service + filename, which imports the three old registries without re-applying anything; an ambiguous bare name is attributed to the first candidate **with a warning**, because silencing it would repeat the defect. **The `audit_log` was never partitioned by month**: migration 002 assumed a job nobody had written, everything piled into `audit_log_default`, and PostgreSQL refuses to create a partition whose range overlaps rows already in the default — the trap tightens over time. `ensure_audit_partitions` now creates the coming months' partitions **and hardens each one against deletion**: the immutability guards are per-table and a new partition does not inherit them. **Three missing access controls**: (1) `POST /ingest/email/poll` required only a valid JWT, and since the process has a single IMAP mailbox with the target entity taken from the header, a user of entity A could pull mail addressed to B into their own — and the poll marks it read, so it never comes back: not an undue read, an irreversible appropriation. The mailbox now declares its owning entity (`IMAP_TENANT_SLUG`, fail-closed) and the endpoint requires `USUA_PERM_ADMIN`, leaving an audit entry per poll; (2) `PATCH /documents/{id}/disposition` set «eliminar» with **read** permission — now `min_crud=3`, with a mandatory rationale, written in the same transaction as its audit entry; (3) the FUID went out with no header: `entidad_productora` is now resolved server-side from `public.tenants`, `unidad_administrativa`/`oficina_productora`/`objeto` are declared per report, and consultation frequency is computed from real accesses in the `audit_log` scoped by `tenant_slug` (the only table shared across entities) instead of estimated. — *Why*: publishing public information is a decision of the entity, not a side effect of not having classified; and a working example key is a known key — *Impact*: **existing radicados become non-publishable** until someone performs the publication act, so an institution using the harvesting channels must expressly publish what it wants disseminated; three environment variables become mandatory before deploying (`SIGNATURE_SECRET`, `MINIO_ACCESS_KEY`, `MINIO_SECRET_KEY`), plus `IMAP_TENANT_SLUG` if email ingestion is used.

- `fix(shared,gateway,*)`: **automatic mail distribution could stop silently while the system kept reporting it was fine (production audit, blocks 9–10)** — four background consumers react to what happens in the system: distributing incoming correspondence, sending email, sealing signatures and feeding the search index. If the internal message broker was unavailable at the exact moment of startup — or restarted afterwards — those consumers **died and never came back**. The system looked healthy: you could register, query and sign. But new documents stopped reaching dependencias, mail did not go out and search kept answering with stale data. Nothing warned. They now restart themselves with exponential backoff, and every failure is recorded. **The health check returned an automatic "all good"**: three services reported healthy **without checking anything** — they said so with the database down. The opposite was also wrong: the gateway declared itself unhealthy when **any** service behind it failed, so the orchestrator restarted the one component still able to serve. There are now two distinct probes — liveness (`/health`, which governs restarts) and a new readiness probe reporting the real state of database, broker, mail and consumers, so the load balancer stops routing to a node that cannot serve without restarting it. Those probes also **leaked internal hostnames and ports** in their error text to unauthenticated callers; they now report state in one word, with the detail left in the server log. **Login failures with no apparent cause**: the pool asked PostgreSQL for more concurrent connections than it grants, on a server shared with the identity system — so under documentary load what failed was **signing in**. The arithmetic is now done, written down and tuned, and a stuck query no longer holds its connection indefinitely. — *Why*: a consumer that dies silently is official correspondence that stops being distributed with nobody noticing, and a health check that always says "fine" disables the very monitoring it appears to provide — *Impact*: images must be rebuilt and the updated production manifest deployed (it tunes the database configuration); anyone monitoring `/health` expecting dependency state must move to `/health/ready`.

- `fix(frontend)`: **hovering the sign-out icon logged you out (production audit, block 9)** — sign-out was a link, and the framework preloads a page's work **when the pointer passes over it**; since the logout happened during that preload, brushing the icon — without clicking — really ended the session. Worse: because the effect lived in a plain GET, a link or an image embedded in an email triggered it too. It now requires pressing a button, and typing the URL by hand lands on a confirmation screen. **Error messages exposed the institution's internal network**: hostnames, addresses and ports appeared on screen; the user now gets a clear message and a **reference code** to quote to support, with the technical detail confined to the server log, plus a branded error page (a broken link used to land on a blank page with raw text and no way back). **The UI could wait forever**: with no client timeout, screens neither errored nor recovered when the backend was slow — including the login screen. There is now a maximum wait, with large downloads (expediente export, preservation package, FUID) explicitly exempt: what gets cut off is a server that does not answer, not one that is sending a big file. **The Back button showed the previous user's tray**: the browser replayed cached pages, so at a shared counter the next officer could see the previous one's radicados and subjects — including classified documents they are not cleared for — and signing out did not prevent it. No screen carrying working data is cached now. A **Content-Security-Policy** is added as a second browser-level barrier against script injected through a document, a template or an assistant reply, even if the existing sanitisation failed. Finally, when permissions fail to load the application **says so**: the menu used to just render empty, indistinguishable from having had permissions revoked — the officer called the administrator, who saw their permissions intact and had nothing to fix. — *Why*: an action with consequences must not happen on hover, and a screen that hides the fact that it is half-working wastes two people's time — *Impact*: sign-out behaves the same when clicked; the frontend image must be rebuilt on deploy.

- `chore(deps,docker)`: **dependencies brought up to date and services stop running as root (production audit, block 8)** — the libraries of all eleven services were updated, including cryptography, the web server and **the one that signs the electronic index**; that is why the change was not accepted by reading the list: the 2,500+ tests and the real-database suites were run first. The frontend moves to Node 22 — the previous line lost support in April 2025 and was what shipped — and to the latest framework release, which carries the request-size fix from the previous block. Ten of the eleven services ran **as root inside their container**; all of them process input they do not control (documents, mail, forms), so a flaw in any library handed over the whole container rather than just the process. They now run as an unprivileged user. And the object-store image stops tracking the `latest` tag: irreversible retention protection lives there, and having it change by itself in a routine update is not acceptable. — *Why*: running as root voids container isolation exactly where untrusted input is processed, and an unsupported release gets no security fixes — *Impact*: no visible change in use; images must be rebuilt on deploy.

- `fix(gateway,auth,frontend)`: **the IP address recorded in the audit trail was chosen by the visitor (production audit, block 7)** — the system trusted a header anyone can write to decide where each request came from. Two consequences: rate limiting was evaded by changing it on each attempt and — worse — **the address stamped into the immutable, evidentiary `audit_log`** was whatever the visitor put there. A chain-of-custody field that can be forged is worse than an empty one, because the empty one deceives nobody. The address is now derived server-side by walking the chain of **declared trusted** proxies and passed internally over a path the visitor cannot alter; with no proxies declared the header is ignored entirely — a useless datum is preferable to a false one. A day-to-day defect went with it: **every user's requests counted as coming from the same address**, because the frontend did not forward the browser's, producing "too many requests" lockouts in an ordinary morning at the counter; and public PQRS intake gets its own stricter limit, since it creates radicados unauthenticated and **consumes numbers that are never reused**. Finally, the audit trail stops writing one entry **per request** to say the token was valid: that buried the facts that matter — accesses, signatures, reclassifications — under enormous noise, making the log unreadable for the very person who comes to investigate. Invalid-token attempts are still recorded. — *Why*: an evidentiary log where nearly every row is noise proves nothing, and neither does an address the visitor picks — *Impact*: the institution must declare its network intermediaries on deploy (`TRUSTED_PROXIES`); without it, per-address limiting does not distinguish users.

- `fix(ci)`: **the automated tests had never run in continuous integration (production audit, block 6)** — the pipeline meant to verify every change died on its **first line**, because of a configuration difference between how it invoked the lint gate and how the project does; since the tool stops at the first failure, **the test run never happened at all** — and the pipeline had been giving the opposite impression for a long time. CI now runs **exactly the same gate** a developer runs locally instead of a copy free to diverge; it runs the eleven services' suites in parallel; and it gains two lanes that did not exist: **real-database** integration tests (256 tests that were written but had never been executed) and **frontend** tests, which had none. Version-tagged image publishing is added too — that is what makes rolling back a failed update possible. Actually running it surfaced three problems reading had not revealed, two of them in the fix itself; they were corrected before accepting it. — *Why*: a pipeline that does not run the tests is not verification, it is decoration — and it grants confidence it has not earned — *Impact*: CI only; no change in system behaviour.

- `feat(infra)`: **backup and restore now really exist, and have been exercised end to end (production audit, block 5)** — the backup procedure lived only as an example inside the guide, and that example **did not work**: it connected as a test user, copied files to a directory that does not exist and — worst — if the dump failed it still produced an empty file **and deleted the previous backups**. Run nightly by cron, that means accumulating months of empty copies that look normal. The recovery procedure, for its part, shut the database down and then tried to restore onto it. There are now two real programs. **Backup** copies database and documents, **verifies the copy can be read** before accepting it, and only then rotates the old ones; if anything is interrupted the copy is marked incomplete and restore refuses to use it. **Restore** requires written confirmation and, on finishing, **verifies the audit trail's hash chain**: that the database starts does not prove the documentary trace is intact, and that is precisely what an entity must be able to attest. If something was tampered with, it says so and points at the entry. The full cycle — copy, destroy, restore, verify — has been executed against a real environment, and the verification was itself put to the test by deliberately altering an entry: it catches it. The **upgrade and rollback** procedure is added too, including the warning that rolling the program back does not roll back schema changes — that is what the backup is for. — *Why*: a backup whose restore has never been tested is not a backup, it is a file; and no institution should put official records into a system without that guarantee — *Impact*: deployment and operations only.

- `fix(gateway,storage,frontend)`: **scanned documents can finally be attached: anything over 512 KB used to fail (production audit, block 4)** — the frontend server shipped a **512 KB** per-request body limit that had never been configured, and since attachments pass through it **any real scanned PDF was rejected** with a terse "upload failed". Bulk expediente import was outright unusable. Raising the limit alone would have been worse: each file was buffered **whole in memory** twice — once at the gateway and once in storage-service — with no size cap at all, so a large file would not have errored, it would have taken the service down. The change therefore does three things at once: files are now streamed **in chunks** without accumulating in memory, there is an explicit cap that returns a clear message when exceeded, and the frontend limit goes to 512 MB. — *Why*: a records-management system where a scanned document cannot be attached does not do its job — *Impact*: attachments and bulk import work; a file above the cap now gets an explicit error stating the maximum size instead of a generic failure.

- `fix(document)`: **editing a radicado now leaves a trace, and an annulment is not undone by editing a field (production audit, block 3)** — changing a radicado's subject, addressee, status or folio count was recorded nowhere — striking, because **reading** it was. An official document with an immutable number that can be edited without leaving a trace does not meet what the documentary trace requires. Moreover an **annulled** radicado — a decision that goes through request and supervisor approval — could return to active status through a plain edit, with no cause, no approver and no record. The system now rejects that and explains why: reversing an annulment, if it is ever warranted, is an act of its own with its own justification, not the side effect of editing a field. Each modification now records **which field changed, from what value to what value**, along with who did it; and if that record cannot be written for any reason, the modification **is not applied** — a change failing is preferable to a change happening untraced. — *Why*: an archival document's traceability admits no gaps, and an annulment undone through a side path is not an annulment — *Impact*: attempting to modify an annulled radicado now returns an explicit error.

- `fix(document,archive)`: **the correspondence register stopped being public by default (production audit, block 2)** — the two harvesting channels (OAI-PMH and CMIS), meant for other institutions and open-data portals to consult what the entity has decided to publish, were **enabled from first boot**, and what they exposed depended on each document being classified as reserved: since a radicado's default is "public", the practice was "everything is published unless somebody remembers". Out went each radicado's number, **subject** and dependencia, and attachment content could be downloaded **with no record of who did it**. These channels now ship **off**, and the entity turns them on when it decides to — which is the right order, because publishing the correspondence register is part of the entity's publication scheme (Ley 1712 art. 12), not part of installing the software. While off they answer as if they did not exist; once on, **every query and every download is recorded** in the audit trail, with what was asked for and how much was returned. — *Why*: what an entity publishes is its own decision, and it needs to be able to answer afterwards for who consulted its archive — *Impact*: **if your institution already used these channels, they must be explicitly enabled** after updating.

- `fix(gateway,tenant,storage)`: **a crooked URL could reach a different place than the one the system thought it was authorizing (production audit, block 1)** — the gateway decided where to route each request by looking at the path as it arrived, but the library that forwarded it **normalized the path afterwards** — the way `..` in a folder path climbs a level. Result: a hand-crafted URL could be authorized as one thing and executed as another. That path reached the institution registry, deliberately kept out of public scope, and allowed replacing or removing a radicado's attachment **without the trace recording who**. The gateway now **rejects** such paths at the door, before authenticating and before choosing a destination. And that is not the only guard: the institution registry and the attachment-mutating operations additionally require their own service credential, so if one of the two protections failed the other still stands. — *Why*: if the front door authorizes one path and executes another, none of its decisions hold. And not appearing in a route list is not a protection, it is an absence — *Impact*: no visible change in normal use.

- `fix(infra)`: **the production deployment manifest had never been executed (production audit, block 0)** — the file describing how to bring OrpycaMCP up in a real institution was written but never run, and it failed in cascade: seven of the eleven services never built, database initialization pointed at a path that does not exist (and Docker, rather than warning, silently mounts an empty directory), the identity manager died at startup on an incomplete certificate configuration, and none of the secrets the services use to talk to each other were defined — which produced no visible error, just an apparently running system where not a single attachment downloads and nobody with a second factor can sign in. On top of that, any server reboot shut the institution down permanently. All of it is fixed and **verified against real containers**, not merely read: the services build, the database runs its initialization and the identity manager starts. The sample environment file now documents every secret, which two services share it, and **which ones must be backed up with the same discipline as the database** — losing the second-factor key forces the entire staff to re-enrol. — *Why*: with no manifest that starts there is no possible deployment, and no other security check can actually be verified — *Impact*: deployment only.

- `feat(archive)`: **TVD — valuation schedule for an accumulated fonds (ADR-026, Increment 1: registration and convalidation, migration 039)** — an entity holding an accumulated fonds (documentation already produced without archival criteria, typical of suppressed units or liquidated entities) had nowhere to register its valuation instrument, and therefore could neither close nor dispose of anything in that fonds. The TVD enters as **the same instrument as the TRD**, with the same convalidation circuit (Comité → Consejo → RUSD → publication): a discriminator on the existing table, not a new table, so the single point on which seven irreversible WORM retention writes depend is not forked. Four layers protect it: a series code can belong to only one instrument; listings are always read through a view that already filters by type; each instrument's own content (fonds, extreme dates, valuation rationale for the TVD) is mandatory or forbidden depending on the type, enforced by the database; and — most important in this increment — **no expediente can yet be classified under a TVD** (the database blocks it outright), so the irreversible-retention risk is zero until that piece exists. Routes `/api/v1/tvd` mirror the TRD ones (create, edit, version, approve, return, convalidate, register RUSD, repeal), same permission as TRD. Full version-history lookup (`GET .../{code}/versiones`) was also added for both TRD and TVD — promised in the previous increment and never built. — *Why*: a records-compliance audit finding on the retention model: an entity with an accumulated fonds had no way to appraise it inside the system.
- `feat(frontend)`: **`/admin/interoperabilidad` — export/import of radicados, batch loading and postal tracking (Phase 8, last of the API↔UI drift closure)** — five backend capabilities had been ready for a while with no screen using them: exporting a ZIP package of radicados, importing it back preserving the original tracking number, creating documents or expedientes in batch, and querying a shipment's tracking against the postal operator. The new screen covers the first four in tabs; the last one was added as an "Update tracking" button in the existing `/envios` tray. The most delicate part is import: it is all-or-nothing (if a single file in the package does not match its declared fingerprint, nothing is imported) and when that happens the screen shows exactly which file failed and why, never a generic "import failed". Batch loading, being a bulk write over official documents, requires confirming the exact item count before executing, and while processing it polls progress every two seconds, always distinguishing "could not query the status" from "no results yet" (a fabricated zero progress is never shown). ### Fixed

- `fix(auth,frontend)`: **the interface offered actions the server was going to reject, because it did not know what level each permission was granted at (third batch of the user-experience review)** — a permission in this system is not a yes or a no: it has a **level** — look up, edit, create or delete. The server knows it and enforces it; the interface never received it, because the lookup that tells it who the user is resolved the level and then **threw it away**, sending only the list of names. The result: someone holding a read-only permission was offered Close, Transfer, Exclude or Sign acta buttons, and got a "you do not have permission" when they pressed them. The two user-experience reviews, carried out separately and blind to each other, reached the same conclusion, and **both refused to fix it screen by screen**: the problem was not in the screens but in what the server tells them. It was fixed in both halves. The server now also sends the level of each permission, **without removing anything it already sent**, so nothing already running breaks and no coordinated update is needed. And the interface learns to ask by level, with a deliberately strict rule: if the level does not arrive — a session opened before this change, for instance — the answer is **no**, never "I don't know, so I'll allow it". Applying it meant reviewing **every** button that writes, one by one, against what its service actually requires. That corrected the finding's own premise: most operations only ask for the lowest level, so **only four screens** needed the high restriction. Requiring more would have been the same mistake in reverse, hiding functions from people who are entitled to use them — and doing so silently. It was noted, without being touched, that the inbox has exactly that shape: the interface asks for a permission the server does not require, because there whoever may act is decided by holding the assigned step, not by a permission. — *Why*: the interface must be a faithful mirror of what the server authorizes; offering what is going to be rejected is a functional failure, not a cosmetic one. — *Impact*: no database changes. 199 authentication-service tests and 1370 frontend tests green, including one that reproduces exactly the reported case.
- `fix(frontend)`: **accessibility: insufficient contrast, tables unreachable without a mouse, errors not announced on their field, and AI suggestions that were never announced (second batch of the user-experience review)** — four problems that left part of the users out. **One**: white text on the brand green did not reach the minimum required contrast, and not in a transient effect but in permanent states — the current step number in the two-factor, signature-credential and signing wizards; the active turn in the signature chain; the active filters in drafts and dispatches. In several places it was **the other way round**: the legible tone was used only on mouse-over. **Two**: wide tables cut off the Status and Actions columns on the right, and those that did scroll could not be scrolled with the keyboard, so anyone not using a mouse could not reach them. It was fixed in the two shared table components, so the fix reaches most screens. **Three**: on the profile screen, all seven validation error messages appeared only as a floating notice and never next to the failing field — precisely on the screen that governs the electronic signature credential; they are now announced on the field, and the one-time codes open the numeric keypad and autofill. **Four**: AI suggestions appeared without notifying screen-reader users; they are now announced, without touching the content, which already met the regulatory requirement to cite sources and warn that it was AI-generated. Two honest caveats: the table containers left unmodified wrap a component whose scrolling is already reachable, and giving them another keyboard stop would have created an empty destination; and the original finding mentioned four tables with one cell too many, which a sweep of all 28 tables in the project **could not reproduce** — recorded as such rather than forcing the figure. — *Why*: an actions column invisible on mobile, or an error a screen reader cannot locate, are not finishing details: they prevent the task from being completed. — *Impact*: 1348 tests green. The two-factor recovery code is deliberately left out: it is a server-side gap and must not be papered over in the interface.
- `fix(frontend)`: **batch loading never reported its result, three administration cards led to "no permission", and two screens were not linked (UX review, first batch of fixes)** — the ~20 screens built to surface everything the backend already exposed were implemented without going through the UX/accessibility review, the last step of the project's process. The review was done afterwards and found three **functional** problems, not cosmetic ones; this is its first batch of fixes. **One**: document and expediente batch loading never reported its result, due to two compounding defects — the progress panel did not refresh, and the screen polled progress at an address that had ceased to exist when the routing was fixed. An administrator could load a thousand radicados and have no way of knowing whether they were created or whether everything failed. **Two**: three cards in the administration panel advertised a permission different from the one the server actually requires, so they led to a "you do not have permission" screen; the Interoperability case was doubly wrong, because it also hid the entire screen from a registration operator who could use part of it. All **sixteen** cards were checked, not just the three found, because this same pattern had already resurfaced four times. **Three**: two finished screens — digital preservation and signing keys — were missing from the administration index, which presents itself as the complete map, and were reachable only by typing the address by hand. The root cause of the first failure was fixed too: several code comments asserted things that had stopped being true (that the gateway did not route batch loading, that the metadata services did not require a permission). This is the third time in this release that a stale comment has caused a real defect, so they were deleted rather than left sitting next to the fix, and tests were added that pin the exact address each screen asks the server for, so a route change cannot silently break it again. — *Why*: a screen signed off as finished and documented as complete had its main function inoperative; building the UI reveals the capabilities, but only the review reveals the UI. — *Impact*: batch loading reports its result; the administration panel stops offering what it will deny and stops hiding what it authorizes; two screens stop being invisible. 1339 frontend tests green.
- `fix(repo)`: **four files of the interoperability screen never made it into the repository** — an exclusion rule written for one specific folder at the project root was written unanchored, so it applied to **any** folder with that name anywhere in the tree. It matched the folder holding the document batch-loading files, which therefore stayed out of the history despite being documented as delivered: in the official copy of the project, the screen called addresses that did not exist there. Fixed by anchoring the rule to the root. — *Why*: it surfaced when re-running the work on a clean copy; the earlier review could not see it, because it reads the working files and there they were present. — *Impact*: none on application behavior. The lesson is that this kind of exclusion fails **silently**: the file simply never shows up as pending to save.
- `fix(document)`: **audit trail for batch radicado creation + reactivation of the batch test suite** — batch radicado creation (`POST /api/v1/batch/documents`) left no trace whatsoever in the immutable audit log: hundreds of official documents, each with a unique tracking number, could be created with no record of who did it or when. It surfaced because the twin batch operation over expedientes, in another service, had done it from day one — two mirror functions, only one leaving a trace. Fixed by writing one audit entry **per radicado created** (not one per batch, so individual traceability is not lost), always attributed to the person who submitted the batch, and in such a way that a partially successful batch (say 480 of 500) records exactly what went in and what did not — never the original intent. In addition, this feature's automated test suite had been fully disabled since it was written (it referenced a test fixture that never existed). It was rewritten from scratch, also covering the permission gate that had recently been added with no test verifying it. — *Why*: mass-creating official documents with no record of authorship is precisely what the audit log exists to prevent; a disabled test suite protects nothing, least of all a freshly added permission gate. — *Impact*: no schema change (the audit table already existed). document-service suite: 284 passing, 20 skipped (previously 273 passing, 25 skipped — the remaining 20 are integration tests against a real database, unrelated to this change).
- `fix(api-gateway,document,archive)`: **batch loading unreachable — missing gateway route and an ambiguous status contract between services** — closes the item left open by the interoperability screen: the gateway had no route registered for `/api/v1/batch/`, so both document and expediente batch loading always returned "route not found". Investigating it surfaced a deeper problem: the two services serving batch loading share the same base path, and the job-status lookup (`.../batch/{id}/status`) had **the identical shape** in both — there is no way for the gateway to guess, from the job id alone, which of the two to ask. The fix nests the status lookup under the job type (documents or expedientes), just as creation already did, so the routing decision is unambiguous. Along the way, document batch loading now requires the same permission as creating a document one at a time — it previously required none, unlike the expediente equivalent. — *Why*: without that route the already-built batch screen could not work; the contract shared by the two services had to be disambiguated at the source, not patched around. — *Impact*: batch status URLs change shape — and the screen consuming them kept the old shape, fixed later in the UX review entry; document batch loading gains permission enforcement. What this change left open — batch radicado creation without an audit entry — is **closed** by the first entry in this release.
- `fix(frontend)`: **accessibility sweep after the v1.0 redesign audit — 27 High/Critical findings (E22, WCAG 2.1 AA)** — AA contrast in `Button` and 8 screens, ≥44px touch targets in 8 components, visible focus in `UserPicker`, a misaligned column on mobile in `/busqueda`, and **explicit confirmation before signing** in `/firmas`, which had none.
- `fix(frontend)`: **redirect loop between Keycloak and `/login` (E22)** — an IdP error returned to `/login` restarted the flow indefinitely; the error is now mapped from a closed table and shown with a "Retry" link.
- `fix(frontend)`: **`//` comments inside `<style lang="scss">` broke the raw SSR build (E22)**.
- `fix(migrations)`: **idempotency guards that did not filter by schema broke the provisioning of the second tenant (multi-tenant)** — guards keyed on constraint/column names repeat across schemas, so from tenant #2 onwards the object was silently skipped. - `fix(scripts)`: **`init_tenant.py` provisioned incomplete tenants and aborted midway (E14/E21)** — two defects: migrations were skipped (knowledge + tenant-service, which silently left PINAR unusable) and migration identity was keyed by bare filename, so collisions between services (archive/document, notification/signature) raised a `UniqueViolation` halfway through provisioning.
